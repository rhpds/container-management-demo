= Role Based Access Control (RBAC)

== Demo flow

=== Know
Position RBAC as the foundation for tenant isolation, least privilege, and controlled delegation.

=== Show
Demonstrate role and binding workflows that enforce access boundaries without slowing delivery teams.

== Introduction

*Role-Based Access Control (RBAC)* in OpenShift is a fundamental security mechanism that determines whether a user, group, or service account is allowed to perform a specific action within a project or the cluster. By applying RBAC to Kubernetes namespaces, OpenShift ensures that multitenant applications remain securely isolated from one another.
Authorization in OpenShift is governed by three primary objects:

* *Rules*: Sets of permitted actions (verbs) on specific objects. For example, a rule dictates whether a user can "create" or "get" pods.
    
* *Roles*: Collections of rules. A single role can contain multiple rules that specify exactly which actions and resources are allowed.

* *Bindings*: The explicit associations that link a user, group, or service account to a particular role.

*Levels of RBAC*

OpenShift evaluates authorization using a two-level hierarchy:

* *Cluster RBAC*: These roles and bindings apply cluster-wide across all projects. A cluster role binding can only reference a cluster role.

* *Local RBAC*: These roles and bindings are scoped to a specific project. While local roles exist only within a single project, a local role binding can reference either a local role or a cluster role. This structure allows administrators to reuse common cluster roles across multiple projects while maintaining the flexibility to customize access inside individual projects through local roles.

*Default Cluster Roles*

OpenShift includes a set of pre-configured default cluster roles that can be bound to users locally or cluster-wide. It is highly recommended not to manually modify these default cluster roles, as altering them can break cluster functionality. Common default roles include:

* `cluster-admin`: A super-user role that can perform any action in any project. When bound locally, it grants full control over every action and resource, including quotas, within that project.
    
* `admin`: A project manager role. If used in a local binding, an admin can view and modify any resource in the project except for the resource quota.
    
* `basic-user`: A user that can retrieve basic information about projects and other users.    

* `cluster-status`: A user that can view basic cluster status information.
    
* `edit` and `view`: Default OpenShift roles that grant standard read/write or read-only access to project resources.

== Demonstration: The Compromised Account

The goal of this demo is not to show how access is granted — that was covered in the User Management section. Here the focus is on what happens *after* a credential is stolen. This framing lands with any audience that has a security team.

[TIP]
====
*"A developer account has been compromised. The attacker has valid credentials and is logged in right now. Let's follow exactly what they can do on this cluster."*
====

`demouser` from the User Management section is already configured with `view` access on the `grafana-demo` project. No additional setup is needed.

=== Step 1 — Impersonate the compromised account

. Navigate to *User Management → Users* and click on `demouser`.
. Click *Impersonate User*.

The console switches to `demouser`'s session.

=== Step 2 — Attempt lateral movement

Try to reach other teams' workloads and cluster infrastructure.

. Open the project dropdown at the top of the console.
. Only `grafana-demo` is visible. `kube-system`, `openshift-monitoring`, `openshift-config`, and every other team's namespace are invisible — they do not appear in the list at all.

[TIP]
====
*"The attacker can't even see other projects exist. There is nothing to enumerate, nothing to pivot to. The blast radius is already contained before a single action is taken."*
====

=== Step 3 — Attempt privilege escalation

Try to grant `demouser` cluster-admin rights.

. Click the *+* (Import YAML) button in the top-right corner.
. Paste the following and click *Create*:
+
[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: demouser-escalation-attempt
subjects:
  - kind: User
    name: demouser
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: cluster-admin
  apiGroup: rbac.authorization.k8s.io
----
+
. The API rejects the request immediately with a clear RBAC error: `clusterrolebindings.rbac.authorization.k8s.io is forbidden`.

[TIP]
====
*"Privilege escalation blocked. The platform does not trust a user to modify their own permissions — or anyone else's. A stolen credential cannot become a cluster-admin credential."*
====

=== Step 4 — Attempt destruction within their own scope

The attacker falls back to damaging what they do have access to.

. Navigate to the `grafana-demo` project.
. Go to *Workloads → Deployments* and click on the Grafana deployment.
. Every destructive action — *Delete*, *Edit*, *Scale* — is greyed out or absent. The `view` role is strictly read-only.

[TIP]
====
*"Valid credentials. Five minutes of effort. Zero damage done. This is what least-privilege enforcement looks like in practice — not as a policy document, but as a technical control that the platform enforces automatically."*
====

=== Step 5 — Stop impersonation

Click *Stop Impersonation* to return to the admin session.

[NOTE]
====
The key message for this audience is not the technical RBAC mechanics — it is the outcome.
OpenShift does not give you the *option* to configure RBAC. It enforces it from day one,
for every workload, every user, and every namespace, without any additional tooling required.
====
