== Demo flow

=== Know
Explain why network segmentation is critical for blast-radius control and zero-trust alignment.

=== Show
Demonstrate policy behaviour and traffic outcomes that prove workload isolation in practice — using the Online Boutique deployed in Chapter 2 as the live target.

== Network Policies

In OpenShift, network policies are tools used to secure your network by controlling the flow of traffic at the IP address or port level between pods and other network endpoints. They apply to the Transmission Control Protocol (TCP), User Datagram Protocol (UDP), Internet Control Message Protocol (ICMP), and Stream Control Transmission Protocol (SCTP) protocols.

OpenShift supports network policies at two primary scopes:

*Namespace-Scoped Network Policies*

Standard `NetworkPolicy` objects operate at the namespace (project) level and are typically managed by developers or project administrators.

* *Default-deny stance*: By default, all pods in a project can freely communicate with each other and external endpoints. However, once you apply a `NetworkPolicy` to a pod, it adopts a "default-deny" stance, meaning it will reject any connection that is not explicitly allowed by a policy rule.

* *Additive rules*: Network policies are additive, meaning you can combine multiple policies together to satisfy complex requirements; a pod will accept connections allowed by at least one of its matching policies.

* *Project templates*: Cluster administrators can modify default project templates to automatically include predefined network policies whenever a new project is created.

*Cluster-Scoped Administrative Network Policies*

Administrators can use `AdminNetworkPolicy` (ANP) and `BaselineAdminNetworkPolicy` (BANP) APIs to define cluster-wide network security configurations.

* *AdminNetworkPolicy*: These policies have a higher priority than standard network policies and enforce cluster-wide security rules that regular users cannot override. They can be configured with an explicit "Allow" or "Deny" action to guarantee connection states, or they can use a "Pass" action to explicitly delegate the policy decision down to the namespace-level `NetworkPolicy` layer.

* *BaselineAdminNetworkPolicy*: This applies a sensible baseline level of network security across the cluster that only takes effect when no other network policy overrides it.

== Demonstration: Isolating a Microservice in a Live Application

This demo uses the *Online Boutique* already running from Chapter 2. No new deployments or YAML setup is needed — the app is the prop.

The audience will watch a real application feature break when a NetworkPolicy is applied, and recover when a surgical allow rule is added. This makes the impact of network isolation tangible without any prior security knowledge.

[TIP]
====
*"I'm not changing the application code. I'm not touching the firewall. I'm going to isolate one microservice with a single policy and show you exactly what that means for the application and for an attacker."*
====

=== Before you start — verify the pod labels

The NetworkPolicy pod selector must match the labels on the cart service pods. Before the demo, confirm the label in use:

. Navigate to the Online Boutique project in the *Topology* view.
. Click the `cartservice` workload.
. Open the *Details* tab and check the *Labels* field.

The standard Google Online Boutique Helm chart uses `app=cartservice` and `app=frontend`. If your chart uses a different scheme (e.g. `app.kubernetes.io/name`), substitute accordingly in the steps below.

=== Step 1 — Show the app working (baseline)

. Open the Online Boutique route (*Networking → Routes* in the Online Boutique project).
. Browse to any product and click *Add to Cart*.
. The cart updates — all services communicate freely, no policies are in place.

[TIP]
====
*"Right now every microservice in this application can talk to every other microservice freely. This is the default. In a real environment, you would want to lock this down so that a compromised service cannot reach payment or user data services."*
====

=== Step 2 — Apply a deny-all policy to the cart service

. In the Online Boutique project, navigate to *Networking → NetworkPolicies*.
. Click *Create NetworkPolicy* and fill in the form:
+
[cols="1,2"]
|===
| Field | Value

| Name | `deny-cartservice-ingress`
| Pod selector — Key | `app`
| Pod selector — Value | `cartservice`
| Policy type | ✅ Deny all ingress traffic
|===
+
. Click *Create*.

image::network-policies.png[Network Policies,1000,1000]

=== Step 3 — Show the application breaking

. Return to the Online Boutique in the browser and refresh the page.
. Click *Add to Cart* on any product.
. The cart operation fails — the storefront degrades gracefully but the cart feature is unavailable.

[TIP]
====
*"One policy. One pod selector. That service is now invisible to the rest of the cluster — including the frontend that needs it. No firewall changes, no application restarts, no code changes. The platform enforced it instantly."*
====

=== Step 4 — Add a surgical allow rule

Now restore cart access — but only from the frontend service. Every other pod on the cluster remains blocked.

. Click *Create NetworkPolicy* again:
+
[cols="1,2"]
|===
| Field | Value

| Name | `allow-frontend-to-cartservice`
| Pod selector — Key | `app`
| Pod selector — Value | `cartservice`
| Add Ingress rule | Allow from pods where Key=`app`, Value=`frontend`
|===
+
. Click *Create*.

=== Step 5 — Verify the app recovers

. Reload the Online Boutique and add an item to the cart.
. The cart works again — only the frontend can reach `cartservice`.

=== Step 6 — Show both policies together

. Navigate to *Networking → NetworkPolicies* and show both policies listed side by side.

[TIP]
====
*"This is zero-trust networking for microservices. The cart service now accepts traffic from exactly one source — the frontend — and rejects everything else. Any other pod on this cluster, in this namespace or any other, is denied. That is east-west traffic control, enforced by the platform, not the application. If the payment service is ever compromised, it cannot reach the cart. If a new pod is deployed without the right labels, it cannot reach the cart. The default is deny — trust is explicit and narrow."*
====

=== Cleanup

To restore the application to its original state, delete both policies:

. *Networking → NetworkPolicies*
. Delete `deny-cartservice-ingress` and `allow-frontend-to-cartservice` from the Actions menu of each.

The application returns to open communication between all services.
