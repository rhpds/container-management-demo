= Container Management Demo
:navtitle: Demo Overview

== How to use this guide

Each chapter follows the same *Know → Show* pattern:

* *Know* — the business context and the "why it matters" talking point, delivered before opening the UI.
* *Show* — a live, console-based demonstration tied directly to customer outcomes.

Every demonstration in this guide is designed to run on a *Single Node OpenShift* cluster without deep platform expertise. No production-scale environment is required.

IMPORTANT: This demo covers *Container Management* use cases — deploying and operating third-party and existing containerized workloads at scale. It is *not* an Application Platform demo. It is not suitable for audiences whose primary interest is using OpenShift to develop, build, and ship their own applications.

== Introduction

A *Container Management Platform* provides a trusted, consistent way to deploy and operate containerized workloads at scale. By abstracting the underlying infrastructure, it makes containers faster to deploy, more portable across environments, and easier to operate. The two primary audiences for this demo are:

* *Independent Software Vendors (ISVs)* — teams delivering containerized COTS workloads to their own customers.
* *Teams running containers built outside OpenShift* — organizations that have existing containerized workloads and need a platform to deploy and manage them reliably.

== Chapter 1: Console Overview

Plain Kubernetes ships a minimal dashboard. OpenShift provides a fully integrated, production-ready web console that manages both standard Kubernetes resources and advanced platform-level requirements — out of the box, with no additional tooling or configuration.

This chapter walks through the five high-value areas of the console most relevant to daily platform operations:

* *The Main Dashboard* — a single-pane-of-glass view of cluster health, capacity, inventory, and live activity. Every card pulls from live Prometheus and Kubernetes API data.
* *The Software Catalog* — a governed, searchable catalog of Operators, Helm Charts, and Templates. The live demo deploys Grafana from the community ecosystem to show third-party software running inside the cluster within minutes.
* *The Events page* — a real-time feed of everything happening in the cluster. The demo uses the Grafana deployment to trigger and read live events, showing how OpenShift makes diagnosis fast without a terminal.
* *The Embedded Web Terminal* — a zero-install browser-based CLI. The demo uses it to retrieve the Grafana admin secret and exec into the running container, showing that platform operations don't require a locally installed toolchain.
* *User Management* — native group and role management directly in the console. The demo creates a user, assigns view access to the Grafana project, and impersonates the user live to show scoped access working immediately.
* *Quick Starts* — guided in-console tutorials that reduce day-one friction. The demo publishes a custom Quick Start from scratch using the Import YAML button, showing how teams can encode their own runbooks as in-console guidance.

== Chapter 2: Deploying COTS and existing applications

OpenShift provides three complementary patterns for deploying third-party and existing software — each optimized for a different level of operational complexity:

=== Operators — the "smart" way

Operators encode human operational knowledge into software. They install, configure, upgrade, back up, and self-repair the application they manage. The demo deploys *Crunchy PostgreSQL* to show the full Operator lifecycle: discovery, installation, custom resource creation, and Day-2 operations.

=== Helm Charts — the "package manager" way

Helm packages all required Kubernetes manifests into a single versioned, templatable unit. The demo deploys *Microsoft SQL Server* from a Helm Chart repository to show how platform-agnostic packaging works inside OpenShift's catalog, without any CLI.

=== Existing applications — the "lift and shift" way

For workloads that already run as container images or have manifests, OpenShift deploys them directly. The demo deploys the *Google Online Boutique* microservices application — a realistic 11-service e-commerce app — as a reference workload used throughout the remaining chapters.

=== Topology view

After the Online Boutique is running, the chapter closes with the *Topology view* — a live graphical canvas of the application's microservices and their interconnections. The demo scales a service and deletes a pod directly from the graph to show continuous reconciliation happening visually, without leaving the console.

== Chapter 3: Secure by default

In a cloud-native environment, security is not a final checklist — it is a continuous, automated layer built into the platform. OpenShift is "secure by default," with three foundational security pillars demonstrated in this chapter:

* *Security Context Constraints (SCCs)* — OpenShift's mechanism for governing what a running pod is allowed to do on the underlying host. The demo shows how attempting to run a privileged container is blocked automatically, and how SCCs are applied without manual configuration.
* *Role-Based Access Control (RBAC)* — The demo takes the "compromised account" angle: using the `demouser` created in Chapter 1, it shows how a constrained identity cannot see other namespaces, cannot escalate its own privileges, and cannot delete workloads it doesn't own — all enforced automatically by the platform.
* *Network Security* — The demo uses the live Online Boutique to show network policies in action: apply a deny-all policy to the `cartservice`, watch the storefront break, then add a surgical allow rule — all from the console, all without touching YAML on the live app pods.

== Chapter 4: Cluster Operations

This chapter makes the same point from three different angles: OpenShift doesn't just get installed — *it manages itself*. Every example runs on the single-node demo environment.

* *Full-Stack OTA Upgrades* — Walk through the Cluster Settings upgrade UI to show the upgrade pipeline, available channels, and rollback path. The demo is a guided tour of the UI; the actual upgrade trigger is reserved as an optional final step after the full demo, since a live upgrade locks out further changes until it completes.
* *Self-Healing by Design* — Two demonstrations: delete a pod from the Grafana deployment and watch the ReplicaSet recreate it instantly; then delete all Online Boutique pods at once and watch the entire application rebuild itself. A third example shows the Machine Config Operator enforcing OS-level configuration on the node itself.
* *OpenShift Lightspeed* — An AI assistant built into the web console. The demo walks through two troubleshooting scenarios: a `CrashLoopBackOff` diagnosed by Lightspeed with root-cause explanation; and an `ImagePullBackOff` triggered live by changing the Grafana image tag to a non-existent value, then asking Lightspeed to diagnose and fix it.

== Chapter 5: Observability — Logging and Monitoring

Plain Kubernetes requires you to assemble your own metrics, alerting, and log aggregation stack. OpenShift ships an integrated observability experience out of the box, and its newest features correlate signals for you automatically. All examples are sized for a Single Node OpenShift cluster.

* *Monitoring your cluster and applications* — Explore the built-in Prometheus-based monitoring stack, execute live PromQL queries, and trigger a real alert through the full alerting pipeline in under a minute. User Workload Monitoring is also demonstrated, showing custom application metrics alongside cluster-level data.
* *Centralized logging with LokiStack* — Shows how logs outlive the pods that produced them. The demo queries logs from a previously deleted pod, searches across namespaces with LogQL, and highlights the difference from vanilla Kubernetes where pod logs disappear when the pod does.
* *Correlating signals with the Troubleshooting Panel* — The Cluster Observability Operator's Troubleshooting Panel lets you jump from a firing alert directly to its related logs and workloads in a single click. The demo shows the "before" (manual, multi-tab investigation) vs. "after" (one-click correlation) contrast clearly.
