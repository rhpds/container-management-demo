= Self-Healing by Design: Continuous Reconciliation

== Demo flow

=== Know
Position OpenShift's control loops as the reason clusters recover from mistakes and failures automatically, without a human re-running a script or SSHing into a box to fix drift.

=== Show
Break something on purpose — a workload, a platform component, and an entire node — live, and watch OpenShift repair it in real time across the three-node cluster.

== Introduction

Every layer of OpenShift is not just installed once and left alone — it is *continuously managed* by a controller that constantly compares "what should exist" (declared in a Custom Resource) against "what actually exists," and reconciles any difference. This same pattern repeats at every layer of the stack:

* *User workloads*: A `Deployment`'s `ReplicaSet` controller keeps the requested number of pods running. This is the well-known Kubernetes pattern, and you already saw it in xref:04-chapter02-01-Using Operators - Crunchy PostgreSQL.adoc[] when a deleted database pod was replaced automatically.
* *Platform components*: Every entry under `Administration -> Cluster Settings -> ClusterOperators` — the console, the image registry, ingress, monitoring, and dozens more — is itself managed by an Operator that continuously enforces its own desired state. These are not install scripts that run once and walk away; they keep watching, forever.
* *Host configuration*: The *Machine Config Operator (MCO)* extends the same reconciliation model down to the operating system itself. Kernel arguments, NTP configuration, SSH keys, and kubelet settings are described declaratively as versioned `MachineConfig` objects, rendered per node pool — not a one-time provisioning script or a manually maintained golden image.
* *Compute infrastructure*: On cloud-backed clusters, the *Machine API* (`Machine` and `MachineSet` resources) takes this one level further — if a VM instance disappears, a `MachineSet` notices and replaces it automatically.

This is the operational story worth making explicit to a technical audience: you do not need a separate toolchain, a scheduled cron job, or a runbook page titled "if X breaks, SSH in and fix it" for a wide class of problems. The platform is opinionated enough to detect and repair drift before a human ever gets paged.

== Demonstration

=== The OpenShift difference vs. vanilla Kubernetes

Before the demos, set the context once:

[TIP]
====
*"On a vanilla Kubernetes cluster, if you delete a system component — the dashboard deployment, the ingress controller — it stays deleted. Nobody brings it back unless someone runs `kubectl apply` again. On OpenShift, every platform component is owned by an Operator that watches it continuously. The desired state is stored, and the platform repairs itself. This is why OpenShift is an opinionated platform and not just a packaged Kubernetes distribution."*
====

=== Example 1: Break a platform component — watch it come back

This is the fastest, most visual way to make the point: delete something core, live, in front of the audience, and watch it come back without anyone touching a keyboard except to break it.

. Open a terminal and look at the `Deployment` currently serving the console page you are looking at right now:
+
[source,bash,role="execute"]
----
oc get deployment console -n openshift-console
----
. Note which node is currently running the console pod:
+
[source,bash,role="execute"]
----
oc get pods -n openshift-console -o wide
----
. Delete the deployment:
+
[source,bash,role="execute"]
----
oc delete deployment console -n openshift-console
----
. You may briefly lose access to the web console if you refresh — that is expected.
. Check the `ClusterOperator` responsible for this component:
+
[source,bash,role="execute"]
----
oc get clusteroperator console
----
. Within roughly 30–60 seconds, watch the *Console Operator* notice the missing `Deployment`, recreate it from its stored desired state, and bring the `AVAILABLE` column back to `True`.
. Check again which node is running the new console pod:
+
[source,bash,role="execute"]
----
oc get pods -n openshift-console -o wide
----
+
The Kubernetes scheduler may have placed it on a *different node* than before — the platform does not just repair the resource, it reschedules it for optimal placement.

NOTE: This is safe to repeat as many times as you like — the Console Operator restores it every time.

=== Example 2: Simulate a node failure — watch workloads migrate live

This is the highest-impact demo on a multi-node cluster. You take an entire node out of service, and the audience watches every pod migrate to the surviving nodes in real time — while the application stays up.

[TIP]
====
*"Imagine this node just suffered a hardware failure — a bad disk, a power supply, a network partition. On a traditional platform, that's an outage. On OpenShift, the platform moves your workloads automatically. Let me show you."*
====

==== Step 1 — Show the starting state

. Open the *Topology* view for the Online Boutique project. All pods should be green and spread across the three nodes.
. Open a terminal and show the pod distribution:
+
[source,bash,role="execute"]
----
oc get pods -n online-boutique -o wide --no-headers | awk '{printf "%-40s %s\n", $1, $7}'
----
+
You will see pods spread across two or three different node names.

==== Step 2 — Pick a node and take it offline

. List the nodes:
+
[source,bash,role="execute"]
----
oc get nodes -o wide
----
. Choose a node that is running several Online Boutique pods (from the output above). Cordon it to prevent new pods from being scheduled there:
+
[source,bash,role="execute"]
----
oc adm cordon <node-name>
----
+
The node status changes to `Ready,SchedulingDisabled`.
. Now drain it — this evicts all pods from the node:
+
[source,bash,role="execute"]
----
oc adm drain <node-name> --ignore-daemonsets --delete-emptydir-data
----

==== Step 3 — Watch the migration

. Switch immediately to the *Topology* view for the Online Boutique.
. Watch the affected pods briefly turn grey (terminating) and then reappear as green (running) — the scheduler placed them on the two surviving nodes.
. Open the Online Boutique route in the browser — **the application never went down**. The storefront is still responsive throughout.
. Verify the new distribution:
+
[source,bash,role="execute"]
----
oc get pods -n online-boutique -o wide --no-headers | awk '{printf "%-40s %s\n", $1, $7}'
----
+
No pods remain on the cordoned node. All workloads migrated to the surviving two.

[TIP]
====
*"I just removed an entire node from the cluster. Every workload that was running there was rescheduled to the remaining nodes in seconds. The application stayed up the whole time. No alert. No runbook. No one on call. This is the same behaviour you get during a planned maintenance window, a rolling OS upgrade, or a real hardware failure."*
====

==== Step 4 — Bring the node back

. Uncordon the node to restore it to the scheduler:
+
[source,bash,role="execute"]
----
oc adm uncordon <node-name>
----
+
The node returns to `Ready` status. Future pod scheduling will use all three nodes again.

NOTE: Existing pods do *not* automatically rebalance back to the restored node — Kubernetes only schedules new pods or pod replacements across all available nodes. This is normal and expected. If you want to demonstrate rebalancing, scale a deployment to 0 and back up, or delete a pod to trigger rescheduling.

=== Example 3: Apply a live OS-level change — rolling reboot with zero downtime

The same reconciliation model extends past Kubernetes objects, all the way down to the operating system. Every node belongs to a `MachineConfigPool`, and every OS-level setting is described declaratively as a `MachineConfig` object.

On a three-node cluster, applying a `MachineConfig` triggers a **rolling reboot** — the MCO cordons, drains, applies, reboots, health-checks, and uncordons one node at a time while workloads keep running on the other two. This is safe to do live.

==== Step 1 — Show the current state

[source,bash,role="execute"]
----
oc get machineconfigpool
----

All pools should show `UPDATED=True`, `UPDATING=False`, `DEGRADED=False`.

[source,bash,role="execute"]
----
oc get machineconfig | grep rendered
----

==== Step 2 — Apply a harmless MachineConfig

This example adds a custom NTP server to the chrony configuration. It is harmless and easily reversible.

. Click the *+* (Import YAML) button and paste:
+
[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-demo-chrony
  labels:
    machineconfiguration.openshift.io/role: master
spec:
  config:
    ignition:
      version: 3.2.0
    storage:
      files:
        - path: /etc/chrony.d/demo-ntp.conf
          mode: 0644
          contents:
            source: data:text/plain;charset=utf-8;base64,IyBEZW1vIE5UUCBzZXJ2ZXIgYWRkZWQgYnkgTWFjaGluZUNvbmZpZwpzZXJ2ZXIgdGltZS5nb29nbGUuY29tIGlidXJzdAo=
----
. Click *Create*.

==== Step 3 — Watch the rolling update

. Navigate to *Compute → Nodes* and watch the node statuses.
. Open the terminal and monitor:
+
[source,bash,role="execute"]
----
oc get machineconfigpool master -w
----
+
The `UPDATING` column changes to `True`. The MCO processes one node at a time:
+
.. Cordons node 1 (`SchedulingDisabled`)
.. Drains all pods to nodes 2 and 3
.. Applies the new OS configuration
.. Reboots node 1
.. Health-checks node 1
.. Uncordons node 1 (`Ready`)
.. Moves to node 2, then node 3
. While the MCO is working through the nodes, keep the Online Boutique open in a browser tab — **the application stays up throughout the entire process**.

[TIP]
====
*"I just changed the operating system configuration on every node in this cluster — live. The platform applied it with zero downtime by rebooting one node at a time and keeping workloads running on the others. This is the same mechanism that runs during a full-stack OTA upgrade: your OS and your platform are updated together, safely, as one automated operation. On plain Kubernetes, there is nothing like this — you SSH into each node, apply changes manually, reboot, hope for the best, and move to the next one."*
====

==== Step 4 — Verify the change

Once `UPDATED=True` returns on the `master` pool:

[source,bash,role="execute"]
----
oc debug node/<any-node-name> -- chroot /host cat /etc/chrony.d/demo-ntp.conf
----

The output shows the NTP configuration you applied — deployed identically to every node, versioned, auditable, and managed by the same control loop that manages everything else on this cluster.

==== Cleanup

To revert the change (triggers another rolling reboot):

[source,bash,role="execute"]
----
oc delete machineconfig 99-demo-chrony
----

IMPORTANT: The rolling reboot takes approximately *5–10 minutes per node* (15–30 minutes total for a 3-node cluster). Plan for this if running the demo live. Alternatively, apply the MachineConfig *before* the audience joins and show the `Completed` result, or apply it during the OTA upgrades section and let it run in the background.
