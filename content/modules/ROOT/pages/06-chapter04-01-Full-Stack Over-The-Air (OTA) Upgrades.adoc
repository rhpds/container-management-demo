= Full-Stack Over-The-Air (OTA) Upgrades

== Demo flow

=== Know
Position OTA upgrades as one supported, versioned operation covering the operating system and the platform together — not a checklist of independently-versioned components to keep in sync yourself.

=== Show
Walk through the update channel and cluster settings screens, explain exactly what happens on this 3-node compact cluster when an update is triggered, and optionally start a live rolling upgrade that the audience can watch.

== The Upgrading Process

Over-the-air (OTA) updates in OpenShift Container Platform are automated updates delivered to the cluster, covering both OpenShift components and the underlying Red Hat Enterprise Linux CoreOS (RHCOS).

The cluster update generally occurs in two main phases:

. *Cluster Version Operator (CVO) target update payload deployment*: The update begins when the CVO queries the OpenShift Update Service (OSUS) for valid update paths based on an update graph. The CVO retrieves the target release image and applies its manifests in separate, logical stages called Runlevels. The CVO ensures that all cluster Operators in the active Runlevel reach a stable state (e.g., reporting Available=True and Degraded=False) before proceeding to the next Runlevel.

. *Machine Config Operator (MCO) node updates*: Once the control plane is updated, the MCO applies the new configuration and operating system to every node. The MCO performs sequential actions on the nodes: it cordons one node to prevent new scheduling, drains all pods to the remaining nodes, applies the operating system update, reboots the machine, health-checks it, uncordons the node — and then moves to the next one.

This is the detail worth pausing on with a technical audience: *the operating system and the Kubernetes platform are versioned, tested, and rolled out together, as a single supported artifact.* You are not separately tracking a base OS patch level, a container runtime version, a CNI plugin release, and an orchestrator version, then hoping the combination has actually been tested together. One update graph, one supported path, one rollback story.

=== Zero-downtime rolling upgrades on this compact cluster

This demo runs on a *3-node compact cluster*, where all three nodes serve as both control plane and worker. The MCO's cordon-drain-reboot-uncordon sequence happens *one node at a time*: while one node reboots, workloads keep running on the other two. This means true *zero-downtime rolling updates* — the same mechanism used in production clusters of any size.

This is the operational story worth making explicit: the upgrade is one fully automated, auditable operation. No maintenance window needed. No SSH. No separate OS patching tool. The cluster upgrades itself safely, node by node, while your applications stay up.

NOTE: For disconnected environments, if your cluster is in a restricted network and cannot access the public internet, you can install a local instance of the OpenShift Update Service. This allows you to mirror the update graphs and release images locally, providing a similar OTA update experience without needing a direct connection to Red Hat's public APIs.

=== Update Channels

In OpenShift Container Platform, *update channels* allow you to declare the minor version you want to update to while choosing the timing and level of support for those updates. The *Cluster Version Operator (CVO)* uses your configured channel and an update graph to provide a list of recommended and conditional updates available to your cluster. You can check your upgrade path online https://access.redhat.com/labs/ocpupgradegraph/update_path[here].

image::update-path.png[Update Path,1000,1000]

Using version 4.22 as an example, the following update channels are available:

* *Fast channel (fast-4.22)*: This channel is updated with new versions of OpenShift Container Platform as soon as Red Hat declares them generally available (GA). These releases are fully supported and intended for use in production environments.
* *Stable channel (stable-4.22)*: Releases are added to the stable channel after a delay from when they were published in the fast channel. During this delay, data is collected from multiple sources and analyzed for product regressions. Once enough data is collected and stability is verified, the release is promoted to the stable channel. Newly installed clusters use the stable channel by default.
* *EUS channel (eus-4.22)*: Offered for all even-numbered minor versions, this channel provides Extended Update Support (EUS). When releases are promoted to the stable channel, they are simultaneously promoted to the EUS channel. The primary purpose of this channel is to serve as a convenience for clusters performing a Control Plane Only update (jumping between even-numbered EUS versions).
* *Candidate channel (candidate-4.22), candidate-4.23, candidate-5*: This channel provides unsupported, early access to releases as soon as they are built. Candidate releases might lack the full feature set of eventual GA releases, have not gone through full Red Hat Quality Assurance, and might not offer update paths to later GA releases. This channel is strictly suitable for testing purposes where destroying and recreating a cluster is acceptable.

== Demonstration

=== Walk through the upgrade UI

. Log in to the web console as a user with the `cluster-admin` role.
. Navigate to *Administration → Cluster Settings*.
. Point out what is visible directly on this page — no separate inventory system needed:
** Current version
** Update status
** Configured update channel
** Available updates list
. Under *Update Channel*, show the available channels and explain the `fast`, `stable`, and `eus` options in the context of what your customer's change management process requires.
. Click through to the available update — show the version, the release notes link, and the *Update* button.
. Explain what happens when you click it: the CVO fetches the release image, applies it Runlevel by Runlevel (each `ClusterOperator` must report healthy before the next Runlevel starts), then the MCO takes over — processing one node at a time: cordon → drain → apply the OS image → reboot → health-check → uncordon → move to the next node. One command, fully automated, OS included, zero downtime.

====

It cordons one node, drains all workloads to the other two, applies the OS image, reboots, health-checks, uncordons — and moves to the next node. The entire cluster stays up the whole time. You are not separately tracking a base OS, a container runtime, a CNI plugin, and an orchestrator version, hoping they have been tested together. One update graph, one supported path, one rollback story."*
====

=== Trigger the upgrade (optional — can be done live)

Because this is a 3-node cluster with rolling upgrades, you can trigger the update live during the demo. The environment stays fully functional throughout.

. Click *Update* on the available version.
. Navigate to *Compute → Nodes* and watch the node statuses — the MCO processes one node at a time:
** Node 1 shows `SchedulingDisabled` → pods drain to nodes 2 and 3 → reboot → returns to `Ready`
** Node 2 takes its turn, then node 3
. While the upgrade progresses, all demo workloads (Online Boutique, Grafana, etc.) remain accessible.

[TIP]
====
*"The upgrade is running right now — and everything else still works. This is a production-grade rolling update: one node at a time, zero downtime. The OS and the platform, upgraded together, automatically."*
====

NOTE: The full upgrade takes 30–60 minutes to complete all three nodes. You can trigger it at the beginning of Module 4 and let it run in the background while presenting the rest of the content, or trigger it at the end of the session and let it complete overnight. The new version — OS and platform together — will be visible on the Cluster Settings page.
