= Centralized logging with LokiStack

== Demo flow

=== Know
Position centralized logging as the fix for the classic "the pod already restarted and the logs are gone" problem, and explain why the modern Loki-based stack fits small environments.

=== Show
Deploy a minimal LokiStack backed by a lightweight object store, then find and correlate application logs that already exist from earlier in the demo.

== Introduction

By default, container logs in OpenShift live only as long as the pod that produced them (``oc logs`` reads directly from the container runtime on the node). Once a pod is deleted, evicted, or replaced — which happens constantly in Kubernetes — its logs disappear unless something has captured them centrally.

*OpenShift Logging* solves this using three components working together:

* *Vector*: A lightweight collector that runs as a `DaemonSet`, tailing container and node logs and forwarding them.
* *Loki Operator / LokiStack*: A horizontally scalable, cost-efficient log store (no Elasticsearch cluster to babysit), queried using LogQL. Logs are organized into three default streams: `application`, `infrastructure`, and `audit`.
* *Logging UI Plugin*: Embeds a dedicated `Logs` view directly inside `Observe` in the OpenShift web console — no separate Kibana or Grafana login required.

TIP: The Loki Operator ships a purpose-built sizing profile called *`1x.demo`*. Unlike the production-oriented `1x.extra-small` and larger profiles, `1x.demo` is explicitly designed for proof-of-concept and small or single-node clusters — it is the right choice for this demo, and for any environment where you want centralized logging without dedicating significant CPU and memory to it.

== Storage prerequisite: a lightweight object store

LokiStack always stores its chunks and indexes in an S3-compatible object store. In production, this is typically Red Hat OpenShift Data Foundation (ODF), Amazon S3, or another cloud provider bucket. For a fast, self-contained demo that doesn't depend on external cloud credentials, we will run a small *MinIO* instance inside the cluster instead.

. Create a project for the logging stack's storage backend (you can use the embedded terminal in the web console):
+
[source,bash,role="execute"]
----
oc new-project demo-logging-storage
----
. Deploy MinIO (use the Quick Create button in the right top side of the web console):
+
--
[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: minio
  namespace: demo-logging-storage
spec:
  replicas: 1
  selector:
    matchLabels:
      app: minio
  template:
    metadata:
      labels:
        app: minio
    spec:
      containers:
        - name: minio
          image: quay.io/minio/minio:latest
          args: ["server", "/data", "--console-address", ":9090"]
          env:
            - name: MINIO_ROOT_USER
              value: minioadmin
            - name: MINIO_ROOT_PASSWORD
              value: minioadmin
          ports:
            - containerPort: 9000
            - containerPort: 9090
          volumeMounts:
            - name: data
              mountPath: /data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: minio-data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: minio-data
  namespace: demo-logging-storage
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 10Gi
---
apiVersion: v1
kind: Service
metadata:
  name: minio
  namespace: demo-logging-storage
spec:
  selector:
    app: minio
  ports:
    - name: api
      port: 9000
      targetPort: 9000
----
--
. Create the bucket LokiStack will write to, using the `mc` client bundled in the MinIO image:
+
[source,bash,role="execute"]
----
oc rsh -n demo-logging-storage deployment/minio \
  sh -c "mc alias set local http://localhost:9000 minioadmin minioadmin && mc mb local/logging-loki"
----
. Install the *Red Hat OpenShift Logging* Operator.
. Create the secret LokiStack will use to reach this bucket:
+
[source,bash,role="execute"]
----
oc create secret generic logging-loki-s3 -n openshift-logging \
  --from-literal=bucketnames=logging-loki \
  --from-literal=endpoint=http://minio.demo-logging-storage.svc:9000 \
  --from-literal=access_key_id=minioadmin \
  --from-literal=access_key_secret=minioadmin
----

NOTE: This MinIO setup is for demo purposes only — a single replica, no TLS, static credentials. It is intentionally minimal so it starts in well under a minute on constrained hardware. Do not reuse this pattern in production.

== Demonstration

=== Step 1: Install the operators

. Go to `Ecosystem` -> `Software Catalog`.
. Filter by `Operators` and install the *Loki Operator* (accept the defaults, cluster-wide install).
. Repeat for the *Red Hat Cluster Observability* Operator. Create an instance for logging.

=== Step 2: Deploy a demo-sized LokiStack

. Create the `openshift-logging` project if it does not already exist.
. Check your cluster's default `StorageClass` (probably `ocs-external-storagecluster-ceph-rbd`):
+
[source,bash,role="execute"]
----
oc get storageclass
----
. Create the `LokiStack` instance (replace `ocs-external-storagecluster-ceph-rbd` with the value from the previous step if it is not the default):
+
--
[source,yaml]
----
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  size: 1x.demo
  storage:
    schemas:
      - version: v13
        effectiveDate: "2024-01-01"
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: ocs-external-storagecluster-ceph-rbd
  tenants:
    mode: openshift-logging
----
--

=== Step 3: Create the collector service account

The `observability.openshift.io/v1` `ClusterLogForwarder` API (OpenShift Logging 6.x, used from OCP 4.16 onwards) does *not* automatically create the collector service account — you must create it and bind its permissions before applying the forwarder.

. Create the service account in the `openshift-logging` namespace:
+
[source,bash,role="execute"]
----
oc create serviceaccount logging-collector -n openshift-logging
----
. Grant log-collection permissions. These `ClusterRole` objects are created by the *Red Hat OpenShift Logging* Operator when it installs:
+
[source,bash,role="execute"]
----
oc adm policy add-cluster-role-to-user collect-application-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  -z logging-collector -n openshift-logging
----
. Grant LokiStack write permission. This `ClusterRole` is created by the *Loki Operator* when the `LokiStack` resource is deployed (complete Step 2 first):
+
[source,bash,role="execute"]
----
oc adm policy add-cluster-role-to-user logging-collector-logs-writer \
  -z logging-collector -n openshift-logging
----

=== Step 4: Trust the LokiStack TLS certificate

The LokiStack gateway uses a TLS certificate signed by OpenShift's internal service CA. The Vector collector rejects this certificate by default, so you must inject the cluster's CA bundle and reference it in the forwarder.

. Create a `ConfigMap` with the service CA injection annotation. OpenShift automatically populates it with the cluster CA within a few seconds:
+
[source,bash,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: lokistack-gateway-ca-bundle
  namespace: openshift-logging
  annotations:
    service.beta.openshift.io/inject-cabundle: "true"
data: {}
EOF
----
. Verify the CA bundle was injected (you should see PEM certificate content, not `{}`):
+
[source,bash,role="execute"]
----
oc get configmap lokistack-gateway-ca-bundle -n openshift-logging \
  -o jsonpath='{.data}' | head -c 100
----

=== Step 5: Apply the ClusterLogForwarder

IMPORTANT: Complete Steps 2, 3, and 4 fully before applying this resource. If the CLF is applied before the service account, the RBAC bindings, or the CA bundle ConfigMap exist, the controller rejects it silently and will not create the collector `DaemonSet`. If that happens, delete the CLF and reapply it after all prerequisites are in place.

. Apply the following manifest:
+
--
[source,yaml]
----
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
    - name: default-loki
      type: lokiStack
      lokiStack:
        target:
          name: logging-loki
          namespace: openshift-logging
        authentication:
          token:
            from: serviceAccount
      tls:
        ca:
          configMapName: lokistack-gateway-ca-bundle
          key: service-ca.crt
  pipelines:
    - name: send-app-and-infra-logs
      inputRefs: ["application", "infrastructure"]
      outputRefs: ["default-loki"]
----
--
. Verify the collector pod is running and successfully pushing logs to Loki (no SSL errors):
+
[source,bash,role="execute"]
----
oc get pods -n openshift-logging
oc logs -n openshift-logging -l app.kubernetes.io/name=collector --tail=10
----

=== Step 6: Find logs that already exist — a callback to Chapter 4

. Wait 1-2 minutes for the collector `DaemonSet` pods to roll out.
. Go to `Observe` -> `Logs` in the console.
. Filter by the `demo-lightspeed` namespace (created earlier in xref:06-chapter04-03-Intelligent Cluster Troubleshooting - OpenShift Lightspeed.adoc[]) and search for `bad-app`.
. Even if that pod has long since been deleted, its `echo starting && exit 1` log line is still here. *This is the punchline*: centralized logging decouples the life of your evidence from the life of your pod.
. Try a free-text search across every namespace, for example `CrashLoopBackOff`, to show how quickly a cluster-wide incident can be triaged from a single screen.
