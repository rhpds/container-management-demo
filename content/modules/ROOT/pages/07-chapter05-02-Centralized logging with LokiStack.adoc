= Centralized logging with LokiStack

== Demo flow

=== Know
Position centralized logging as the fix for the classic "the pod already restarted and the logs are gone" problem, and explain why the modern Loki-based stack fits small environments.

=== Show
Find logs from a pod that no longer exists — proving that logs outlive the containers that produced them.

== Introduction

By default, container logs in OpenShift live only as long as the pod that produced them (`oc logs` reads directly from the container runtime on the node). Once a pod is deleted, evicted, or replaced — which happens constantly in Kubernetes — its logs disappear unless something has captured them centrally.

*OpenShift Logging* solves this using three components working together:

* *Vector*: A lightweight collector that runs as a `DaemonSet`, tailing container and node logs and forwarding them.
* *Loki Operator / LokiStack*: A horizontally scalable, cost-efficient log store (no Elasticsearch cluster to babysit), queried using LogQL. Logs are organized into three default streams: `application`, `infrastructure`, and `audit`.
* *Logging UI Plugin*: Embeds a dedicated `Logs` view directly inside `Observe` in the OpenShift web console — no separate Kibana or Grafana login required.

TIP: The Loki Operator ships a purpose-built sizing profile called *`1x.demo`*. Unlike the production-oriented `1x.extra-small` and larger profiles, `1x.demo` is explicitly designed for proof-of-concept and small or single-node clusters — it is the right choice for this demo, and for any environment where you want centralized logging without dedicating significant CPU and memory to it.

[NOTE]
====
*Pre-demo requirement:* The full LokiStack stack (MinIO, Loki Operator, OpenShift Logging Operator, LokiStack instance, ClusterLogForwarder) must be deployed before this section. Allow 10–15 minutes on a fresh cluster. See xref:00-initial-setup.adoc[Initial Setup] for step-by-step instructions.
====

== Demonstration

=== Step 1: Open the Logs view

. In the *Administrator* perspective, navigate to `Observe` -> `Logs`.
. You are now looking at a centralized stream of logs from every pod on the cluster, organised into the three default streams: *application*, *infrastructure*, and *audit*.

[TIP]
====
*"On vanilla Kubernetes, there is no built-in log aggregation. You assemble your own stack — Fluentd or Fluent Bit, Elasticsearch or Loki, Kibana or Grafana — and you maintain it. On OpenShift, this view was available the moment the logging stack was deployed. No custom dashboards, no index patterns, no log pipeline YAML to maintain by hand."*
====

=== Step 2: Find logs from a deleted pod

This is the core story of centralized logging.

. In the namespace filter, select the `demo-lightspeed` project (created during the Lightspeed section of Chapter 4).
. Search for `bad-app` in the free-text search field.
. The `echo starting && exit 1` log line from the crashed pod appears — even though that pod was deleted long ago.

[TIP]
====
*"That pod no longer exists on this cluster. But its log is here. Centralized logging decouples the life of your evidence from the life of your container. In a production incident, this is the difference between having a forensic trail and having nothing."*
====

=== Step 3: Search across all namespaces

. Clear the namespace filter.
. Search for `CrashLoopBackOff` across all namespaces.
. Any pods that have recently crash-looped across the entire cluster appear in a single view — no need to know which namespace to look in, no need to `oc logs` pod by pod.

[TIP]
====
*"This is how a platform team does triage. One search, one screen, entire cluster. Compare this to logging into individual nodes or running `kubectl logs` across dozens of namespaces one at a time."*
====

== Pre-demo setup reference

The following is provided for reference. Complete all steps in xref:00-initial-setup.adoc[Initial Setup] before the demo.

=== Storage prerequisite: MinIO

LokiStack always stores its chunks and indexes in an S3-compatible object store. For a fast, self-contained demo that doesn't depend on external cloud credentials, a small *MinIO* instance runs inside the cluster.

. Create the `demo-logging-storage` project.
. Deploy MinIO using the *+* (Import YAML) button:
+
[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: minio
  namespace: demo-logging-storage
spec:
  replicas: 1
  selector:
    matchLabels:
      app: minio
  template:
    metadata:
      labels:
        app: minio
    spec:
      containers:
        - name: minio
          image: quay.io/minio/minio:latest
          args: ["server", "/data", "--console-address", ":9090"]
          env:
            - name: MINIO_ROOT_USER
              value: minioadmin
            - name: MINIO_ROOT_PASSWORD
              value: minioadmin
          ports:
            - containerPort: 9000
            - containerPort: 9090
          volumeMounts:
            - name: data
              mountPath: /data
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: minio-data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: minio-data
  namespace: demo-logging-storage
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 10Gi
---
apiVersion: v1
kind: Service
metadata:
  name: minio
  namespace: demo-logging-storage
spec:
  selector:
    app: minio
  ports:
    - name: api
      port: 9000
      targetPort: 9000
----
. Create the bucket:
+
[source,bash,role="execute"]
----
oc rsh -n demo-logging-storage deployment/minio \
  sh -c "mc alias set local http://localhost:9000 minioadmin minioadmin && mc mb local/logging-loki"
----

=== Operators and LokiStack

. Install *Red Hat OpenShift Logging* Operator (cluster-wide) from OperatorHub.
. Install *Loki Operator* (cluster-wide) from OperatorHub.
. Create the S3 credentials secret:
+
[source,bash,role="execute"]
----
oc create secret generic logging-loki-s3 -n openshift-logging \
  --from-literal=bucketnames=logging-loki \
  --from-literal=endpoint=http://minio.demo-logging-storage.svc:9000 \
  --from-literal=access_key_id=minioadmin \
  --from-literal=access_key_secret=minioadmin
----
. Deploy the `LokiStack` instance:
+
[source,yaml]
----
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  size: 1x.demo
  storage:
    schemas:
      - version: v13
        effectiveDate: "2024-01-01"
    secret:
      name: logging-loki-s3
      type: s3
  storageClassName: ocs-external-storagecluster-ceph-rbd
  tenants:
    mode: openshift-logging
----

=== Collector service account and ClusterLogForwarder

. Create the service account:
+
[source,bash,role="execute"]
----
oc create serviceaccount logging-collector -n openshift-logging
----
. Bind log-collection permissions:
+
[source,bash,role="execute"]
----
oc adm policy add-cluster-role-to-user collect-application-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user collect-infrastructure-logs \
  -z logging-collector -n openshift-logging

oc adm policy add-cluster-role-to-user logging-collector-logs-writer \
  -z logging-collector -n openshift-logging
----
. Inject the cluster CA bundle:
+
[source,bash,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: v1
kind: ConfigMap
metadata:
  name: lokistack-gateway-ca-bundle
  namespace: openshift-logging
  annotations:
    service.beta.openshift.io/inject-cabundle: "true"
data: {}
EOF
----
. Verify the CA bundle was injected before continuing:
+
[source,bash,role="execute"]
----
oc get configmap lokistack-gateway-ca-bundle -n openshift-logging \
  -o jsonpath='{.data}' | head -c 100
----
. Apply the ClusterLogForwarder:
+
IMPORTANT: Complete all steps above fully before applying this resource. If the CLF is applied before the service account, the RBAC bindings, or the CA bundle ConfigMap exist, the controller rejects it silently and will not create the collector `DaemonSet`.
+
[source,yaml]
----
apiVersion: observability.openshift.io/v1
kind: ClusterLogForwarder
metadata:
  name: instance
  namespace: openshift-logging
spec:
  serviceAccount:
    name: logging-collector
  outputs:
    - name: default-loki
      type: lokiStack
      lokiStack:
        target:
          name: logging-loki
          namespace: openshift-logging
        authentication:
          token:
            from: serviceAccount
      tls:
        ca:
          configMapName: lokistack-gateway-ca-bundle
          key: service-ca.crt
  pipelines:
    - name: send-app-and-infra-logs
      inputRefs: ["application", "infrastructure"]
      outputRefs: ["default-loki"]
----
. Verify the collector is running:
+
[source,bash,role="execute"]
----
oc get pods -n openshift-logging
oc logs -n openshift-logging -l app.kubernetes.io/name=collector --tail=10
----

NOTE: This MinIO setup is for demo purposes only — a single replica, no TLS, static credentials. It is intentionally minimal so it starts in well under a minute on constrained hardware. Do not reuse this pattern in production.
